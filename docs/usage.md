# Использование

Запуск, направления миграции и логика переноса.

## Запуск

```bash
node git-migrate.js
```

При старте скрипт определяет направление: из `MIGRATION_DIRECTION` либо интерактивным вопросом в терминале.

## Направления

### GitLab → GitHub

1. Получает список проектов из группы-источника GitLab (`GITLAB_GROUP_ID`) через API с пагинацией.
2. Для каждого проекта обеспечивает наличие репозитория на GitHub (`ensureGitHubRepo`), создавая его как `private`, если он отсутствует.
3. Имя по умолчанию сохраняется как в источнике (`USE_ORIGINAL_REPO_NAME`).

### GitHub → GitLab

1. Получает список репозиториев владельца GitHub (`GITHUB_OWNER`, тип — `GITHUB_OWNER_TYPE`).
2. Определяет namespace назначения в GitLab (`GITLAB_TARGET_NAMESPACE_ID` или личный namespace токена).
3. При `PRESERVE_SOURCE_OWNER_AS_GITLAB_GROUP=true` создаёт/использует подгруппу с именем owner из GitHub и создаёт проект внутри неё (`ensureGitLabProject`).

## Как это работает

Для каждого репозитория выполняется единый конвейер:

1. **Список источника** — через REST API (GitLab/GitHub) с обходом пагинации.
2. **Создание цели** — идемпотентные функции `ensure*` создают репозиторий/проект/подгруппу только если их нет; все цели создаются `private`.
3. **Перенос истории** — `git clone --mirror` (или `git fetch --prune` для уже существующего локального зеркала) из источника в `MIRROR_ROOT`, затем `git push --mirror` в назначение.
4. **LFS (опционально)** — при `MIGRATE_LFS=true` дополнительно переносятся LFS-объекты.

git-команды запускаются через обёртку над `child_process.spawn`.

## Безопасный прогон и обработка ошибок

- При `DRY_RUN=true` реальные изменения не выполняются — это рекомендуемый первый шаг.
- Ошибка по отдельному репозиторию логируется (`Failed: <name> -> ...`) и не прерывает обработку остальных.
- При наличии сбоев итоговый код выхода — ненулевой (`process.exitCode = 1`).
