# Архитектура: Layered (слоистая)

## Обзор

Проект — небольшая однофайловая CLI-утилита на Node.js для зеркальной миграции репозиториев между GitLab и GitHub. Доменная сложность низкая, внешних зависимостей нет, команда — один разработчик. Для таких задач избыточны Clean Architecture или DDD: они добавляют церемонию без выгоды. Слоистая архитектура даёт ровно столько структуры, сколько нужно — чёткое разделение между разбором конфигурации/CLI, обращением к внешним API и git-операциями, при этом всё остаётся простым и быстрым в развитии.

Логически код уже организован послойно внутри `git-migrate.js`; данный документ фиксирует эти границы как правила, а не предписывает дробление на множество файлов раньше, чем это понадобится.

## Обоснование решения

- **Тип проекта:** standalone CLI-утилита (пакетная миграция git-зеркал)
- **Технологический стек:** JavaScript, Node.js 18+, CommonJS, без фреймворка и БД
- **Ключевой фактор:** низкая сложность + один файл + один разработчик → ценится скорость и простота, а не строгая изоляция слоёв

## Структура папок

Сейчас вся логика живёт в `git-migrate.js`, сгруппированная по слоям. По мере роста извлекайте слои в отдельные модули, сохраняя то же направление зависимостей:

```
git-migrate.js              # Текущая реализация — все слои в одном файле
.env.example                # Конфигурация окружения (шаблон)

# Целевая структура при росте (по желанию):
src/
├── cli/                    # Слой представления: выбор направления, ввод/вывод, main()
│   └── prompt.js           # askDirection, normalizeDirection
├── config/                 # Загрузка и валидация конфигурации из окружения
│   └── env.js              # loadEnvFromFile, сборка объекта config
├── clients/                # Слой доступа к внешним API (HTTP)
│   ├── gitlab.js           # gitlabRequest, getGitLabProjects, ensureGitLabProject ...
│   └── github.js           # githubRequest, getGitHubRepos, ensureGitHubRepo ...
├── git/                    # Слой git-операций (обёртки над git CLI)
│   └── mirror.js           # run, ensureMirrorUpToDate, pushMirror
├── migration/             # Бизнес-логика: сценарии миграции по направлениям
│   ├── gitlab-to-github.js
│   └── github-to-gitlab.js
└── utils/                  # Кросс-срезовые помощники
    └── naming.js           # sanitizeRepoName, buildGitHubRepoName, buildGitLabProjectPath
```

## Правила зависимостей

Зависимости направлены строго вниз: верхние слои вызывают нижние, но не наоборот.

```
CLI / main()  →  migration  →  clients (API)  +  git  →  utils / config
```

- ✅ `cli` вызывает `migration`
- ✅ `migration` вызывает `clients` и `git`
- ✅ Любой слой может использовать `utils` и читать `config`
- ❌ `clients`/`git` не знают о `migration` и `cli`
- ❌ Слой представления (`cli`) не вызывает напрямую git-операции в обход `migration`
- ❌ `utils`/`config` не зависят от вышестоящих слоёв

## Взаимодействие слоёв

- **CLI → Migration:** `main()` определяет направление и для каждого репозитория вызывает соответствующий сценарий (`migrateGitLabToGitHub` / `migrateGitHubToGitLab`).
- **Migration → Clients:** сценарии получают список источника и обеспечивают наличие цели через API-функции (`getGitLabProjects`, `ensureGitHubRepo` и т.п.).
- **Migration → Git:** сценарии выполняют перенос истории через обёртки git (`ensureMirrorUpToDate`, `pushMirror`).
- **Ошибки:** пробрасываются вверх; пакетный цикл в `main()` ловит ошибку по отдельному репозиторию, логирует и продолжает, отражая итог в коде выхода.

## Ключевые принципы

1. **Не перепрыгивать слои:** `cli` не обращается к API/git напрямую — только через `migration`.
2. **Конфигурация — на границе:** все переменные окружения читаются и валидируются в одном месте на старте; ниже передаётся уже готовый `config`.
3. **Идемпотентность операций назначения:** функции `ensure*` создают репозиторий/проект/подгруппу только если их нет.
4. **Безопасность по умолчанию:** уважать `DRY_RUN`; целевые репозитории создавать `private`; токены — только из окружения.
5. **Изоляция сбоев:** ошибка одного репозитория не прерывает миграцию остальных.

## Примеры кода

### Направление зависимостей: сценарий миграции опирается на слои API и git

```javascript
// migration: бизнес-логика оркестрирует clients + git, но не CLI
async function migrateGitLabToGitHub(project) {
  const repoName = buildGitHubRepoName(project);          // utils
  await ensureGitHubRepo(repoName, project.description);  // clients (API)

  const localMirror = path.join(config.mirrorRoot, `${repoName}.git`);
  await ensureMirrorUpToDate(localMirror, gitlabUrlWithToken); // git
  await pushMirror(localMirror, githubUrlWithToken);           // git
}
```

### Конфигурация читается один раз на границе и передаётся вниз

```javascript
// config: единая точка чтения/валидации окружения
for (const key of REQUIRED_ENV) {
  if (!process.env[key]) {
    console.error(`Missing required env var: ${key}`);
    process.exit(1);
  }
}
const config = { /* собранные значения из process.env */ };
// Нижние слои используют config.dryRun, config.mirrorRoot и т.д.,
// но сами process.env не читают.
```

## Анти-паттерны

- ❌ Вызов git-операций или API напрямую из слоя представления в обход `migration`.
- ❌ Чтение `process.env` в глубине слоёв вместо использования собранного `config`.
- ❌ Хардкод токенов/URL внутри функций вместо передачи через `config`.
- ❌ Прерывание всей миграции из-за ошибки одного репозитория.
- ❌ Преждевременное дробление на множество модулей/абстракций раньше реальной необходимости — сохраняйте простоту, пока файл управляем.
